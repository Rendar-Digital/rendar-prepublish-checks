# Issue lifecycle (enforcement contract, not activated)

The enforcement switch returns `false` unconditionally, even with `RENDAR_PC_ENFORCEMENT=true`. No issue, scheduler or notifier file is loaded by plugin boot; no mail or cron is queued. The files can be loaded independently in stub tests. This is **not** authorization to enable enforcement or deploy.

When a later phase unlocks the gate, its save-time backstop calls `rendar_pc_queue_issue($post_id, $intent)`; the scheduled re-check calls the same function with `source=cron` and `dispatch_owned=true`. The outermost `wp_after_insert_post` or the end of `publish_future_post` finalizes from an uncached status read. The finalizer writes a post-meta record, then fires **`rendar_prepublish_checks_issue_finalized`** (provisional enforcement internal hook; `$post_id`, `$record`, `$report`; action, three args). `held` means the final uncached read returned `pending`, never merely that a hold was attempted. The `rendar_prepublish_checks_schedule_failed` (four args), `rendar_prepublish_checks_backstop_demoted` (five args, only if held), and `rendar_prepublish_checks_failure_recipients` filter are also provisional enforcement internals, **not public v1 contracts**. See `docs/API.md` for the public v1 surface; issue hooks and the route need an explicit versioned public contract before enforcement is unlocked. Notifications subscribe to the finalized event, deduped by post, failure checks, intended schedule and measured outcome. A failed `wp_mail()` releases only its own atomic options claim for retry; WordPress mail returning true does **not** prove delivery.

`/rendar-prepublish-checks/v1/issue/<post_id>` is an enforcement-only read route. It requires `edit_post` for the requested ID, including for administrators; anonymous and unauthorized users receive the REST authorization error. Issue meta is private, not registered for general REST exposure. The admin queue requires `edit_others_posts`. The editor watcher must only poll when enforcement is available. An `unavailable` check is not a passing verdict and cannot resolve a stored failure, even when core publishes in the same scheduled cron dispatch. A later independent publish or complete evaluation may resolve it; the incomplete marker is post-scoped and cleared at dispatch end. If a callback throws before the dispatch-end hook runs, the shutdown recovery finalizes outstanding intents and clears abandoned dispatch/incomplete markers even if no intent was queued; it does not swallow the exception or clear unrelated issue records. A caller that catches the exception and publishes the *same post again before shutdown* is not covered by this recovery mechanism and needs separate handling before enforcement can be unlocked.

## Durable storage keys

- `rendar_pc_settings` (option), `rendar_pc_activated` (watermark option).
- `_rendar_pc_schedule_failure` (serialized issue post meta), `_rendar_pc_scheduled_by` (user ID post meta), `_rendar_pc_schedule_override`, `_rendar_pc_override`, `_rendar_pc_override_log`, `_rendar_pc_first_published`, `_rendar_pc_decorative` (post meta).
- `rendar_pc_notified_` + MD5 fingerprint (non-autoloading wp_options atomic claims, 30-minute TTL); `rendar_pc_notice_` + user ID (short-lived transients). Claim values are `<timestamp>:<owner uuid>`; expiry reads the numeric timestamp prefix.

Do not delete records or claims merely because enforcement is dormant.

Verification: `bash tests/run.sh`, `bash tests/build-zip.sh` (builds a local dist artifact; never installs/sends). Stub lifecycle tests do not prove WordPress cron dispatch, REST capability mapping in real core, concurrent MySQL claims, or mail delivery. Those require explicit real-WP acceptance before unlock.
